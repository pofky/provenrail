I told Claude Code to run rm -rf src in a repo where src held two files I had never committed. It did, and its reply was: "Deleted src (untracked, so not recoverable from git)." Then I ran pr undo last and both files came back, byte for byte.

Claude Code can rewind its own file edits, and its docs say "Checkpointing does not track files modified by Bash commands". A shell command is how a working tree actually gets lost: rm -rf, git checkout ., a formatter pointed at the wrong directory, a script the agent wrote a minute earlier. So this takes the snapshot in the one place that sees every action, the pre-tool hook, and it snapshots the tree instead of the file the tool says it will touch, because a shell command does not say.

How it works. A second git object store lives outside your repository, under ~/.provenrail. Before any tool call that can write, the hook stages the working tree into that store's own index and writes a tree object. Your real .git is never opened: no stash, no commit, no ref, nothing in git status. A restore first snapshots the current state, so an undo can be undone, and a full restore is checked by tree hash before it prints "Verified". On a 381 file repo the first snapshot took 1.04 s and each one after it 0.03 s. Read-only calls take no snapshot and cost about 8 ms extra.

What it does not cover, because a recovery tool that overstates itself fails at the worst moment: files your .gitignore excludes (apart from root level .env files), files over 50 MiB, commits and branches in your real repo, nested repos and submodules (recorded as a pointer and never touched by a restore), databases, and anything outside the repository. Checkpoints are kept for 14 days. If a snapshot cannot finish in 10 seconds it pauses for that project and says so. It is a way back from a mistake, not a backup.

The same hook does four other things I wanted for running agents unattended. pr stop refuses every tool call from every agent running the hook on the machine until pr resume. A loop breaker asks you after the same call or the same short cycle repeats 8 times back to back; I picked 8 by replaying 3,186 of my own sessions, where 97.1% never repeat a block at all and 0.47% would have been asked once. When two sessions share a checkout, the second is asked before it edits a file the first wrote in the last 15 minutes. And an optional phone remote sends approval questions to Telegram or ntfy with no server of mine in the path; a missing answer or a dead network leaves the verdict as it was, and it never waits past the hook timeout, because a host that kills a hook treats it as having no opinion. It guards against a trusted agent's mistakes while you are away, not against hostile software running as you.

Honest limits on the hosts. The hook has adapters for Claude Code, Codex, Gemini CLI, Copilot and Cursor. I have driven it end to end on Claude Code only. The other four are written from each vendor's documented hook contract and I would like to hear where they break.

Install in Claude Code is two lines and needs nothing else on the machine, it runs on the system python3: /plugin marketplace add pofky/provenrail, then /plugin install provenrail-guard@provenrail.
